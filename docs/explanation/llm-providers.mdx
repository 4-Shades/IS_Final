## Two providers, one interface

The agents can use either of two language-model providers, chosen by `LLM_PROVIDER`:

- **Ollama** (`ollama`, the default) runs an open model, `llama3.2:3b`, on your own machine. It's free and works offline, but it's slow without a graphics card.
- **OpenAI** (`openai`) calls `gpt-4o-mini` over the internet. It's fast and cheap, about $0.001 per trip plan, but needs an API key and credits.

Both sit behind the same interface in `common/llm.py`, so the agents don't know which one they're using.

The self-hosted setup uses Ollama because it costs nothing. The cloud setup used OpenAI because running a model in the cloud needs about 3 GB of disk and 4 GB of memory per instance, which the small hosting plans used here couldn't provide, and larger ones cost far more than OpenAI's per-request price.

## Getting reliable JSON

The UI needs flights, stays, and activities in an exact shape it can put in a table. Language models write free text by default, so the agents constrain what the model can produce, then check the result.

**Constrain.** Each agent passes the JSON schema of its expected response, generated from the Pydantic model, to the provider:

- Ollama receives it in the `format` field, which limits generation to JSON matching the schema.
- OpenAI receives it as a `json_schema` response format in **strict** mode. Strict mode accepts only a subset of JSON Schema: every object must forbid extra fields and list all its fields as required, and keywords such as defaults or length limits aren't allowed. `to_openai_strict_schema` converts the Pydantic schema into that subset.

Both use temperature 0, for the most predictable output.

**Check.** The answer is always validated again against the full Pydantic model, including the rules strict mode had to drop, such as prices of zero or more. If validation fails, the agent returns an `error` instead of passing along bad data.

The prompt also includes an example of the expected JSON, which helps smaller local models that follow schemas less reliably.

## When the model fails

A model call can fail in several ways: the provider is unreachable, it times out, it rejects the request (for example, no OpenAI credits left), or it returns JSON that fails validation. All of these become the same kind of error inside the agent, and the agent responds with "... planner is temporarily unavailable." rather than crashing. The real cause, including OpenAI's own error message, goes to the agent's log.

## Curated guidance

Before asking the model, Flight, Stay, and Activities each look up a few passages from [Wikivoyage](https://en.wikivoyage.org), the open travel guide, and add them to the prompt. This is retrieval-augmented generation (RAG): the model writes its suggestions with relevant, real guidance in front of it, instead of relying only on what it remembers. The trip plan lists the passages as sources.

### Building the index, ahead of time

An ingest command (see [Build the guidance index](/how-to/build-the-guidance-index)) does the slow work once:

1. **Download** each destination's Wikivoyage article through the MediaWiki API.
2. **Keep useful sections.** Articles follow a standard layout (Get in, See, Do, Eat, Sleep, and so on), so each agent can be given the sections that fit its job, and the rest are left out.
3. **Split** sections into passages of about 300 tokens, with [LlamaIndex](https://www.llamaindex.ai)'s sentence splitter, so each one is a focused piece of text.
4. **Embed** each passage, turning it into a vector that captures its meaning, with the same provider the agents use (`embeddinggemma` on Ollama, or OpenAI's embedding model).
5. **Store** the vectors, text, and metadata (destination, section, source URL, license, and validity dates) in [Chroma](https://www.trychroma.com), a vector database kept in a local folder.

### Looking up guidance, per request

When a request arrives, each agent:

1. **Resolves the destination** to an ingested one, allowing listed aliases ("NYC" for New York City). If it isn't in the index, the agent skips retrieval entirely.
2. **Embeds a short question** about its own topic, such as "where to stay, neighbourhoods, and accommodation in Paris." The question is deliberately not the whole prompt: dates and budgets would only add noise to the search.
3. **Searches** for the most similar passages, filtered to that destination, the agent's own sections (Sleep, Stay safe, and Understand for Stay), English, and guidance that hasn't expired.
4. **Adds the top two** to the prompt, clearly marked as reference material.

### Designed to fail quietly

Retrieval is an improvement, not a requirement. If there's no index, the destination isn't covered, the embedding model is unavailable, or the lookup takes over 30 seconds, the agent plans the trip exactly as it would without guidance, and logs why. Retrieval never turns a working trip plan into an error.

### Guarding against the retrieved text

Wikivoyage is edited by anyone, so retrieved text is treated as untrusted. It's wrapped in `<guidance>` markers with an instruction to treat it only as reference data, any copies of the markers inside the text are removed so it can't break out of them, and its total length is capped. Sources come from the index, never from the model: the JSON shape the model must produce has no field for them, so it can't invent citations.

### Trade-offs

- **Speed.** Each passage is extra text for the model to read. On a CPU-only machine, two passages per agent kept trip plans within the normal range of plan times; three made them noticeably slower. `RAG_TOP_K` controls it.
- **Coverage.** Only ingested destinations get guidance, and only by exact name or listed alias.
- **Freshness.** Passages expire a year after they're downloaded and are then excluded until the index is rebuilt.
- **Large cities.** Wikivoyage splits big cities into district articles. The planner reads only the main article, so some sections, like Sleep for Paris, are general rather than specific.
